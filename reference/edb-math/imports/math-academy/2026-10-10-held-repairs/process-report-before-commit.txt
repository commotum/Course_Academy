Math Academy question recovery and attributed repair in EDB
Process report, 10 October 2026

The governing approach is to preserve what Math Academy actually supplied, then make any corrections as separately attributed contributions. EDB's immutable history supports this directly: original assertions remain attributable and recoverable even after their current values or entities are retracted and replaced. We can maintain accurate current content without keeping obsolete facts current solely for audit purposes.

The final preparation covered all 26 questions left after the larger held-question recovery. It produced two sequential EDN transactions: original content under :org/Math-Academy, followed by repairs under :agent/gpt-6-astra-ultra. Both stages passed a sequential speculative preview against durable basis 187. Nothing in this final two-stage package was committed. The preview successors 188 and 189 were hypothetical database values; the live database remained at 187, and the held index retained all 26 questions.

Earlier in the recovery, three GPT-6.1-sol agents at high reasoning reviewed the then-remaining 839 questions individually. That pass resolved 813 questions with 834 verified answer fields: 709 new questions and 101 updates were committed, while three questions were already current. Those verified commits advanced the database from basis 165 to 186. The 26 remaining cases had actual content or answer-uniqueness concerns. They were no longer blocked by routine matching, missing field bindings, or schema capacity. The subsequent preparation read the live database again and found basis 187; it did not assume that the earlier basis was still current.

The distinction between recovery and repair matters. Recovery establishes what the source said and which captured answer it intended. Repair changes that content so the resulting question is mathematically sound and sufficiently unambiguous. A model can interpret a saved Math Academy solution without becoming the author of that solution. Once it changes the wording, mathematics, answer choices, or explanation, those changed claims need the model's own attribution.

Model selection and delegation were part of the quality control. The bulk source-recovery work used GPT-6.1-sol/high. For the final substantive repairs, the user required GPT-6-astra at ultra reasoning. The two repair-authoring workers were replaced with Astra/ultra workers before their drafts were used. One Astra agent authored the 19 ambiguity repairs, another authored the seven other defect repairs, and they independently reviewed each other's completed proposals. A third Astra/ultra agent checked EDB conventions and implemented the read-only sequential preview helper.

For future difficult mathematical recovery and repair, the operating policy is to use GPT-6-astra/ultra, or the highest available GPT model suitable for the work with the strongest suitable reasoning configuration. Resolve the actual available model when starting the work and record the model and reasoning setting that really ran. This policy is not a claim that one model name will always be the highest available. In this run, the execution configuration was model gpt-6-astra with reasoning effort ultra; :agent/gpt-6-astra-ultra is the corresponding EDB source identifier. Another model must not be given that attribution merely because the same workflow or prompt was used.

A more capable model still needs evidence and verification. Each worker received a disjoint set of current held IDs, original captures, and a defined output record. Its job was to identify the intended answer, cite the supporting source, explain the requested field or result, propose exact old-to-new changes where necessary, and check that the repaired question had a unique correct choice. Delegation reduced elapsed time and kept the coordinating agent's context manageable. The coordinator assembled and checked the outputs rather than treating an agent's confident conclusion as proof. The evidence records and common-situation log make the work inspectable after the agents finish.

The current held index is the starting point for every recovery pass. Older analysis files may contain useful candidates, but they also contain already resolved questions. Intersect them with the current index before assigning work. Read the current database basis before planning, and use that same basis for the snapshots that drive the plan. A prepared transaction is tied to observed state; if that state changes, compare the changes and revalidate before any later submission.

The source evidence comes from the original capture, not an old normalized answer label. state.json records before-answer fields and choices, submissions, grading, and later observations. content.json supplies normalized content and knowledge-point associations. Saved HTML establishes field placement and original values where normalization is incomplete. Asset manifests connect original image URLs to the saved bytes. Existing proposed correct answers, correct_origin labels, and learner submissions are candidates, not independent authority: many captured activities intentionally submitted incorrect answers.

A question is complete only when every answer field is verified against the same captured question version and layout. The reviewer must bind a value to the requested field, proof step, table cell, vector entry, or conclusion. Finding a matching expression somewhere in the solution is insufficient if it is only an intermediate quantity or an incidental variable. Conversely, a requested intermediate result may appear earlier in the worked solution rather than at its end. Many of the original holds came from these interpretation and extraction problems, including paraphrases, compound answers, equation chains, domain qualifiers, and damaged layout. A proof question with many fields increases the verification work; it does not by itself require a new schema.

Preservation must be exact enough to retain mathematical meaning. Keep singleton set braces, full factors, nested matrix rows and columns, vector components, units, and parameter restrictions. Empty MathML rendered as dollar signs is not an answer. Preserve the original choices in the original-content stage. Restore layout from captured HTML rather than guessing, and normalize both image choices and their correct values consistently. Original image bytes use the shared content-addressed path images/xx/hash.ext; explanations, source evidence, preparation metadata, and receipts stay under Course_Academy/reference/edb-math/imports/math-academy/. Only transaction EDNs and image assets belong in the relevant SSD locations.

The last 26 questions illustrate why a hold is not synonymous with a wrong answer. Nineteen had a valid Math Academy answer alongside another mathematically valid choice. One correctly answered “no x-intercepts” while incorrectly describing an empty real locus as a circle. One used a coefficient-matrix convention that conflicted with the ordinary full-augmented-matrix reading. Five had an incorrect or unsupported answer for the question as written, including undefined or impossible premises. This classification directed the smallest useful repair. It avoided treating every disagreement as a reason to replace the answer key.

The two-stage transaction design makes the authorship boundary concrete:

1. The original-content transaction represents the captured Math Academy version, including its known errors, under :org/Math-Academy. It prepares 23 new questions and updates three existing question records. Question UUIDs are preserved where already present. Original choices and intended keys are recovered from source evidence; an agent's independently derived answer is never silently substituted into this stage.

2. The repair transaction carries :agent/gpt-6-astra-ultra. It changes only the content required to remove errors or ambiguity, plus the component structure required to represent changed answer fields. Unchanged question identities, knowledge-point membership, and other attributes are not reasserted under the agent source.

EDB accepts one explicitly supplied source per transaction. The source is an entity reference supplied with the transaction request; it is not inferred from the authenticated submitter, execution tool, filename, or model configuration. All resulting assertions and retractions carry that source, including changes automatically generated by EDB. The two EDN files must therefore be submitted separately, in order, with their respective source arguments. A single transaction cannot express both source attributions.

Attribution is not a certificate of mathematical correctness. It answers who supplied the assertion. A faithfully imported but incorrect Math Academy answer still belongs to Math Academy's source. A correction belongs to the agent that authored it. Retracting an MA assertion under the agent source records who withdrew it; the original historical assertion retains its MA attribution. Retractions match the entity, attribute, and value independently of the original source, so the repair source identifies the retractor rather than limiting removal to facts previously asserted by that source. The current question can consequently contain a mixture of unchanged MA facts and repaired agent facts. There is no need to relabel the entire question as agent-authored.

The repairs were deliberately local. Twenty-five prompts, eleven worked solutions, and two choice values changed across the 26 questions. All original MA-intended choice indices were retained in the preparation records. The captured indices identify source choices; EDB stores the choices as an unordered cardinality-many relationship. Fourteen ambiguous integral questions were made to ask for the integrand obtained pointwise from the specified construction, preventing a different expression with the same final integral value from also answering the question. Line and axis questions gained natural direction, parameter-origin, or eigenvalue-order requirements. The sequence with an undefined first term starts at n=2. The false circle claim becomes a real-locus question and loses its misleading diagram. A purported nonexistent quadratic curve becomes a question about the well-defined quadratic form.

For the duplicate Taylor-series choice, changing one exponent in the distractor made it distinct while preserving the source's correct answer and solution. Small solution defects were repaired where necessary, including an incorrect equation reference, a wrong derivative label, and wording that failed to acknowledge a curve's piecewise smoothness. These were targeted corrections to the captured material, not broad rewrites or newly invented exercises. repair-diff.txt shows every exact text and choice change; the author proposals explain why each change is needed.

EDB immutability is the reason this can be done cleanly. A transaction produces a new database value. Ordinary current-state reads omit retracted facts, while historical reads expose the original additions and subsequent retractions. Updating the current content does not mutate a previously captured database value. The earlier claim that obsolete field and answer facts needed to remain current to preserve their history was too restrictive and was corrected during this work. Ordinary retraction is the appropriate way to retire current facts that have been superseded.

Use the smallest suitable operation. For prompt and solution strings, which are cardinality-one attributes, the repair uses compare-and-swap with the exact expected old value. EDB checks that expectation against the preceding database value, retracts the old value, and asserts the replacement. Both the removal and addition carry the agent source. A separate explicit retraction would be redundant. Keeping the same question entity preserves the question's identity while its content evolves.

For the two revised choice sets, the repair uses :db/retractEntity on the superseded answer field and creates a replacement field with its own answer entities. This follows the local field-scoped answer convention: an answer entity belongs to one field and is not shared between the old and replacement fields. Even unchanged option text therefore receives a new component identity inside a replacement field. This structural work is necessary for the selected field-replacement approach; it does not make the unchanged mathematical values into additional content corrections.

Entity retraction has a wider effect than removing one ownership link. EDB retracts the entity's own facts, recursively retracts component descendants, and removes incoming reference-valued facts. Before using it, inspect exactly which references it will remove. Here, the two affected fields and their ten answer entities were introduced by the original-content stage. The preview verified that no external incoming references or learner responses would be removed. The repair retired exactly those twelve entities from current state. It retained the question entities and attached their replacement fields.

History preservation is subject to the database's retention configuration. Attributes marked :db/noHistory can lose superseded values, and deliberate excision can remove historical data. Neither should be confused with ordinary correction. The schema snapshot for this run found no noHistory settings, and the actual speculative history checks recovered the original data. This is stronger evidence than relying only on a general statement that the database is immutable.

Validation followed the transaction sequence. The first transaction was applied to an immutable in-memory database value at basis 187, producing speculative basis 188. The second was applied to that exact successor, producing speculative basis 189. Two independent previews against the original live basis would not establish that the stages compose correctly. The helper used EDB's DatabaseValue.with_edn operations without opening a writer or publishing either transaction.

The checks covered the complete resulting questions and answer fields, preserved question UUIDs, exact knowledge-point membership, canonical image references, every datom's source, and the exact planned retractions. The original stage produced 804 speculative datoms with six planned retractions. The repair stage produced 173 speculative datoms with 86 planned retractions. Those retractions include text replacements and the field-component cascades; they are not 86 separate editorial changes.

The historical proof used the repaired speculative database itself. Reading it as of the first stage recovered all 26 original Math Academy questions and their original component graphs. All 174 original field/answer component entities remained recoverable historically; 162 also remained unchanged in the current speculative state, while twelve were retired. Each removed fact retained its original assertion and source in history alongside the agent-attributed removal. A fresh read of the durable database still returned basis 187.

Stable identifiers matter across the stages. The second EDN uses lookup references based on question and field UUIDs, rather than copying speculative numeric entity IDs or reusing first-stage tempid strings. Tempids are local to a transaction, and speculative numeric allocations are not reservations for a later commit. This allows the prepared stage to describe logical identities correctly while keeping the preview's allocation details in its evidence records.

Preparation and commitment remain distinct states. The two EDNs are ready for review and later authorized submission, but preparation did not remove anything from the held index. A future commit pass must check the then-current basis, validate the sequence against any changed state, submit the original stage followed by the repair stage with the correct sources, and verify the durable receipts and readbacks. Only verified committed results justify removing the questions from the held index. At the end of this preparation, all 26 were prepared and all 26 remained listed as held pending commitment.

The reusable procedure is therefore: select the current unresolved IDs; freeze the relevant database and source evidence; assign disjoint source-recovery and repair work to suitably capable agents; verify every field and every claimed source; preserve the source version in its own attributed transaction; author minimal corrections under the actual repair author's source; use retractions and replacements according to the schema; preview the stages sequentially; prove both the current result and historical recoverability; and update completion records only after the authorized commit has actually been verified.
