# 6. Database Commit

Python commits the validated transactions from Database Preparation. This stage uses no agent judgment about content or entity identities.

1. Connect to the existing writer for `/media/jake/SSD/EDB/math`. If a prior submission exists, recover its outcome and finish verification before starting a new one.
2. Preview the prepared EDN against the database version (basis) used during preparation. Check the proposed additions, retractions, and source attribution. A changed basis or validation failure returns to Database Preparation for reconciliation and a fresh preview.
3. Save the complete request before submitting, including the exact EDN, database target, source, UUIDs, expected basis, and unique request key.
4. Commit batches in dependency order, with one source per transaction. Use a basis guard so concurrent writes cannot silently invalidate the prepared changes.
5. If the response is missing or unclear, recover the receipt or retry the identical request with the same key. Establish its outcome before changing the transaction or creating a replacement request.
6. Read back the affected entities at the receipt's committed database version. Verify content, relationships, and sources; check the receipt for unexpected changes, including learner or engine facts. Confirm that preparing the same capture against that version produces no further content changes. If verification fails, recover the receipt and retry the read. Route a confirmed mismatch to Preparation for reconciliation; retain the confirmed commit and never treat it as uncommitted or blindly resubmit it.
7. Save the transaction, preview, receipt, and verification with the capture under `reference/`. Mark the import complete only after verification. Report success or durably saved pending work to the capture loop; only that loop selects the next activity.

Python classifies commit outcomes and routes rejected plans back to Database Preparation. Source-content gaps return to Activity Capture's agent through Preparation for a decision now. An interrupted commit or verification resumes from its saved state; it never causes the Math Academy activity to be repeated.

Bind each prepared snapshot and new durable request to EDB's immutable database lineage, in addition to its configured connection and basis. Check that lineage before submitting or reusing a saved receipt. Rebuilding a database under the same name does not make its numeric entity IDs interchangeable with the previous database. Retain a request with a different or unknown lineage unchanged for reconciliation; never silently retarget it or replay an old migration transaction.

Speculative previews use the same native schema predicates as the deployed writer, including answer-field validation. The capture preview helper can only evaluate `with`; it cannot commit or start a writer. Normal reads and durable submissions continue through the configured EDB CLI and writer socket.

Keep completed captures, agent decisions, original images, and pending database work durably under `reference/` before selecting another activity. Retry temporary writer or connection failures with backoff while capture proceeds.

Process pending captures through the shared database queue and lock. Accumulate complete activities across accounts until a compatible group contains at least 200 distinct supported questions, including canonical examples and existing questions. This is a minimum, not an approximate target; the last whole activity can take the group above it. There is no automatic time, activity-count, byte-target, or operation-target flush below the minimum. Small queues remain durable until enough compatible questions arrive. EDB does not prescribe a universal batch size.

Prepare every activity in a group against one immutable basis. Combine only compatible, same-source information sets: shared additive practice-pool memberships can be merged, but conflicting revisions must remain in order across separate batches. Defer a conflicting activity and later activities depending on it while gathering unrelated activities to reach the minimum. Include an activity's supported questions, answer fields, mappings, tutorials, and route together. Enforce separate 8 MiB / 50,000-operation safety limits; these prohibit unsafe submissions and never force an automatic small commit. If no safe group reaches the floor, retain the work for later accumulation or reconciliation. Retain an oversized activity with an explicit pending reason instead of silently splitting it. A configured derived source still requires its own transaction.

Persist an immutable activity manifest and a complete exact request under `reference/mathacademy/capture-database/batches/<target>/<batch>/`. Recover an active group before starting later queued work. Verify the full group receipt and reprepare each member at its committed basis. Copy the shared request and receipt into each activity's existing evidence archive so its import status, omissions, and new/existing question counts remain inspectable. If source content changes during recovery, first establish the original request's outcome, then leave the revised capture queued for a new import. Existing individual pending requests are recovered before batching new work.

`drain` and `drain --once` respect the question minimum. Only explicit `drain --flush` permits an underfilled group, for example when deliberately finishing a course's remaining imports. Recovery of an already saved exact request is independent of the new minimum: an unknown outcome must always be established, even if that older request was small.

Establish any unknown commit outcome before later writes, and reprepare against the current basis when required. Pending persistence is distinct from completed question judgments; it is never reported as a successful import. Recovery runs automatically without asking Jake or exiting the capture loop. If durable storage itself is unavailable, retain the current state and retry saving before advancing.

When a verified import supplies a previously missing KP pool, requeue older captures whose retained source was omitted for that dependency. Keep their previous omission visible until re-preparation and verification finish. Probe each newly supported canonical example once per dependent capture; a failed unchanged retry must not loop. This source-only reconciliation never replays learner activities or alters an unresolved saved request.

The runner display separates **Pending imports** from **Omissions**. Pending imports await database processing or verification. Omissions counts terminal imported captures that excluded unsupported content; it is a count of captures, not questions. A verified transaction confirms the supported changes and does not claim that omitted content was imported. Preserve each omission's final reason in the database result, and display pending failure reasons separately.
